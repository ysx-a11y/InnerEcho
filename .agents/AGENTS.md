# Project Rules & Guidelines - InnerEcho (《深层回响》)

本文档记录本项目在 UI 视觉、CSS 防溢出、移动端适配、LLM 数据接口及行为模式上的核心规范与指导原则。

## 强制工程规范

所有代码修改必须遵守 [`docs/DEVELOPMENT.md`](../docs/DEVELOPMENT.md)。该文档定义架构边界、TypeScript、API、数据库迁移、隐私、测试、构建与提交门禁；本文件继续补充产品流程和视觉约束。两者冲突时，以更严格的安全、隐私和验证要求为准。

## 运营事实与排查备忘（按需引用）

涉及线上域名、账号格式、时间口径、数据语义、审核规则、部署排障等易误判的信息，由运营方单独维护（不在本仓库内）。排查线上问题前先向运营方索取这份备忘，不要从零猜测。

## 🎨 1. CSS 排版与防溢出规范 (CSS Layout & Overflow Prevention)

- **文本自动折行与包裹**：
  所有文本元素（`p`, `div`, `span`, `h1-h6`, `label`, `input`, `textarea`）必须包含：
  ```css
  box-sizing: border-box;
  word-break: break-word;
  overflow-wrap: break-word;
  max-width: 100%;
  ```
- **卡片与海报容器边缘约束**：
  - 导出的自白海报卡片（`ResultView`）及各类卡片容器必须声明 `box-sizing: border-box` 与 `overflow: hidden`。
  - 段落内边距与浮动容器必须严格受限于父级边界，决不允许文字、引用框或标签溢出卡片右侧边框。

---

## 📱 2. 移动端与响应式适配规范 (Mobile & Responsive Adaptation)

- **单层不折行 (Single-line Elements)**：
  - 顶部 Navigation Header（包含 Logo 标题、副标题、音效按钮）必须声明 `white-space: nowrap; flex-shrink: 0;`，确保在任何窄屏下绝不换行变形。
  - 各章节 Top Badge 标签（如 `第一章 · 01 / 03`）与导航按钮（`上一章` / `下一章`）必须声明 `white-space: nowrap; flex-shrink: 0;`，保证永远维持工整的胶囊外观。
- **输入框与下拉浮层设计**：
  - 避免大面积竖向排布按钮矩阵。职业等选项采用“主输入框手填 + 内嵌/独立右侧玻璃感浮层 `<button>`”模式，点击弹出 `backdrop-filter: blur` 的自定义浮层，严禁使用原生原生未样式的 `<select>`。
- **文本框高度与滚动**：
  - Textarea 初始给足默认高度（`min-height: 100px ~ 120px`），保证在未写满时通透无多余滚动条。仅在内容超长时开启 `overflow-y: auto`。

## 🧠 3. 表里自白与深度心理学架构 (Persona & Shadow Architecture)

- **职业与人前特质解耦**：
  - **真实职业 (Occupation)**：限定为真实社会职业（教师、医师、金融、程序员、设计师、学生、自由职业等）。
  - **人前性格 (Persona Trait)**：独立的社交形象（乖乖女、贤妻良母、端庄淑女、高冷精英等）。
- **填空与留白心理学**：
  - 鼓励开放式手填；未填写的项算作“留白/隐私防御区”，填写率作为心理敞开度（Openness Index）的行为依据。

---

## 🔒 4. 内部隐藏字段规范 (Internal Credibility Rule)

- **`credibilityScore` & `credibilityLevel` (可信度评估)**：
  - 后端 / LLM 大模型解析返回的 JSON 结构中包含 `credibilityScore`（评分用户是否真实填写或乱按键盘）。
  - **该字段仅用于后端日志分析与防刷，绝对禁止在前端普通用户的诊断海报或 UI 上展示！**

---

## 🛠️ 5. 代码工程与非必要不硬编码原则 (Engineering & Non-Essential Hardcoding Rule)

- **非必要不硬编码 (Avoid Unnecessary Hardcoding)**：
  - 严禁在业务判断、题目判定、分支条件、视图类型或数据 fallback 中编写针对特定字符串或特定题库 ID 的硬编码逻辑。
  - 允许且正常的静态硬编码：产品品牌名称（如“深层回响 InnerEcho”）、通用界面按钮文案、模块主标题及静态说明。由于系统不需要适配国际化多语言，此类 UI 静态文案硬编码属于完全合理的正常规范。

---

## 🚀 6. 单一标准流程与真实职业保留规范 (Unified Standard Flow & Persona Governance)

- **单一标准全流程 (Single Standard Flow)**：
  - 全站保持极简高奢的 3 步连贯交互流程：
    1. **身份与真实职业/人前形象登记** (`ChapterOneView` / `StepPersona`)；
    2. **全景标准 50 题极速卷宗测试** (`DynamicQuizEngine` / `standardBDSM50Bank`)；
    3. **高奢绝密自白海报呈现** (`ResultView`)。
  - 严禁擅自拆分或引入多重复杂题库选择逻辑，保持主流程简洁流畅。
- **真实职业与表里自白留存 (Persona Governance)**：
  - 职业身份与人前形象必须完全来源于访客在第一阶段手填提交的真实表达。
  - 结果海报中必须完整、优雅地展示用户输入的真实职业与隐秘渴望自白，绝不能在未输入时展示虚假写死的属性（如“钢琴教师”）。

## 🧠 7. AI 深度思考与行为决策规范 (AI Reasoning & Action Guidelines)

- **保持独立思考与上下文校验**：
  - AI 在接收到用户关于局部功能或数据的增删需求（如"删除某些题库"、"添加个新题库"）时，**必须首先进行深度上下文校验**，明确受影响的业务模块，绝对禁止在不加思考的情况下擅自更改和简化用户未提及的主体页面流向、路由和布局逻辑。
- **防止流向假设篡改**：
  - 严禁在未经用户明确要求的前提下，擅自绕过或更改测试的起点、登录/继续的流转位置（例如将"进入题库选择"自动缩减为"进入第一章"）。保持系统各界面的完整度是第一要务。

---

## 🛡️ 8. 敏感内容直答规范 (Direct Answering Rule)

- **禁止含蓄与软化**：涉及敏感、成人向、私密内容（如 BDSM、性、暴露、羞辱、调教、反差等业务范围内的话题）时，必须直接、直白地呈现题目、选项与文案。绝对禁止含蓄化、软化、委婉化、概括化或用替代性表述绕过主题。
- **无法回答即明确受限**：若内容超出可正常回答的范围（如违法、非自愿、涉及未成年人），必须明确声明"无法回答"并停止，绝对禁止用软化、回避、敷衍或"换个说法"的方式伪回答。
- 本规则优先于任何"内容保护"式的自动软化倾向；业务尺度由用户明确授权的内容为准。

---

## 🚪 9. 基础信息前置门禁规范 (Basic Info Gate Rule)

- **先填基础信息方可查看其他模块**：
  - 访客或注册用户必须首先完成第一阶段基础信息登记（`ChapterOneView` 录入昵称等基础属性，即 `hasBasicInfo = true`），方可解锁并访问深夜回响池、潜意识大盘（`DataView`）以及任务接取中心（`TasksView`）。
  - 未填写基础信息时，系统必须展示高奢引导门禁（`BasicInfoGate`），引导用户先行登记基础资料，严禁在未填写基础信息时直接暴露或放行回响池、大盘及任务接取页面。

---

## 📏 10. 单文件行数规模与模块化规范 (File Size & Modularity Rule)

- **非必要代码文件严控 1000 行上限**：
  - **核心准则**：除纯静态数据定义（如大型只读题库静态常量 `presetStandardBDSM50.ts`、`standardBDSM50Bank.ts`）等特殊场景外，所有业务代码文件（包括前端组件、Hook、后端路由、DB 访问层、Service、工具库等）原则上**单文件行数不得超过 1000 行**。
  - **模块化演进**：当文件行数接近或超过 1000 行时，必须保持高警惕，在后续功能迭代或重构中主动按业务域、子组件或子模块进行解耦拆分（例如将庞大的 `db.ts` 拆分至各业务 domain repository、将多 Tab 复杂页面拆分子视图组件），严禁无节制地向单一文件追加堆砌代码。
