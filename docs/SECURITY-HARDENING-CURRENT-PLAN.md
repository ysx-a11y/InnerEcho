# InnerEcho 当前安全加固实施清单

> 用途：记录本轮代码审查后的最终执行口径，避免后续重复讨论或扩大防御范围。
>
> 核心目标：在不明显增加普通用户端请求、弱网负担和廉价服务器压力的前提下，优先降低刷票、自动化探测、管理端异常访问以及“数据库已被动过但没人知道”的风险。

## 一、最终决策

### 1. 投票：只做轻量限制

- 同一可信 IP 在 24 小时内最多发起 20 次投票。
- 当前不叠加设备指纹、验证码、行为评分或复杂风控。
- 设备 ID 可更换、换 IP 可绕过，记录为阶段性技术债；后续只有在真实滥用出现时再升级。
- 限流应尽量只影响投票接口，不影响普通浏览、答题和报告提交。

### 2. 原审查问题 2、5、6：按已确认方案修复

- 这三项属于本轮需要实际落地的修复项，完成后必须补对应测试并纳入上线门禁。
- 不因为预防性安全需求继续增加用户端验证码、额外往返请求或高成本检查。
- 具体验收以原审查记录中的问题描述和代码证据为准；如果实现过程中发现需要新增外部权限，转入“外部依赖”区，不在代码里假设已经具备。

### 3. 蜜罐：保存来源 IP，累计触发后多次永久封禁

- 正常用户没有访问蜜罐路径的理由，命中后记录来源 IP、路径、UA 和触发次数。
- 首次命中默认临时封禁 24 小时。
- 累计第 3 次命中后升级为永久封禁；后续继续命中仍保留永久状态并累计记录，不因临时封禁过期而清除历史触发次数。
- 本地回环地址保留白名单，避免开发、测试和健康检查误封。
- 蜜罐拦截异常时，仍返回统一的隐藏式响应；安全记录失败不能拖垮正常业务。

### 4. 提交提示：保持现有位置

- 提交按钮下方的提醒如果当前实机观察已经足够醒目，就不移动、不增加额外弹窗或确认步骤。
- 只保留与数据公开展示、保存和隐私相关的必要说明。

### 5. 资源边界：保留“按接口分级”的轻量方案

- 普通 JSON/表单请求使用较小上限。
- 只有确实需要媒体或大载荷的分析、任务完成等接口使用较大上限。
- 大载荷接口增加独立的低频限流，避免超大请求在解析前持续消耗内存和 CPU。
- 题库文字内容按现有校验上限处理；两三千字规模不应单独触发高成本防御。
- 普通用户端不增加验证码、额外确认页或安全审计请求，因此弱网体验不因本轮加固明显变差。

## 二、当前代码状态

### 已经落地

- 投票接口：可信 IP / 24 小时 / 20 次的轻量限流。
- 蜜罐：持久化来源 IP，默认 24 小时封禁，累计 3 次升级永久封禁。
- 请求资源边界：普通请求与媒体/大载荷请求分级解析，并对昂贵接口做低频限流。
- 既有审查修复：真实客户端 IP、日志脱敏、数据库备份、密钥持久化、数据库权限和日志轮转等以既有审查记录为准。

### 当前工作区已搭建、尚未提交

当前未提交改动包含管理端安全审计基础设施：

- 新增 `security_events` 表，保留 90 天并按天清理。
- 管理端请求结束后记录审计元数据：请求 ID、来源 IP、UA、路由、状态码、耗时和目标摘要。
- 不记录令牌、请求体、搜索词或业务响应正文。
- 事件使用 HMAC 链串联，管理端可检查当前保留区间是否被篡改。
- 新增管理接口读取安全事件，并对以下情况生成异常事件：
  - 新的管理登录来源；
  - 短时间内多次登录失败；
  - 短时间内集中读取敏感管理数据。
- 审计写入在响应结束后异步执行，写入失败只记服务端错误，不阻塞管理请求。

## 三、接下来只做这些代码内工作

### A. 完成安全审计架子并验证

- 为安全事件仓储补单元测试：写入、分页、90 天清理、HMAC 链校验、篡改检测、空表行为。
- 为管理审计中间件补测试：成功登录、失败登录、401/403/429、404 探测、敏感读取、删除操作和普通静态访问分类。
- 补管理接口测试：无令牌 401、合法令牌可查询、分页参数校验、响应不包含令牌或业务正文。
- 检查 SQLite 写入异常、并发请求和迁移升级路径。

### B. 把审计结果接入管理端

- 管理端增加安全事件查看入口，默认展示最近事件和严重度。
- `chainValid = false` 时在管理端显示醒目告警，并保留事件详情供排查。
- 对“新管理来源、登录失败突发、敏感读取突发、蜜罐永久封禁”提供明确筛选。
- 管理端不以弱网为约束，可以使用分页、筛选和更完整的详情；不向用户端暴露这些数据。

### C. 做一次安全回归

- 验证正常用户浏览、答题、提交和弱网重试不受额外审计请求影响。
- 验证投票第 20 次允许、第 21 次被拒绝，跨 24 小时后恢复。
- 验证蜜罐首次、第二次、第三次和后续命中状态，确认永久状态不会被临时封禁清理掉。
- 验证普通题库和两三千字题库内容不会触发不必要的大请求策略。
- 验证审计链遭到修改时管理端能发现，而非静默显示“正常”。
- 通过 `npm run typecheck`、`npm test`、`npm run build` 后再提交。

## 四、需要外部条件，先记录不在本轮假设完成

### 需要服务器/反向代理权限

- 部署数据库迁移和新服务端代码，并观察审计事件增长量。
- 确认 nginx/Cloudflare 的真实 IP 透传链路没有被改回错误配置。
- 在 Cloudflare/WAF 或 nginx 层增加扫描路径、异常频率和明显自动化工具的规则；这属于边缘/服务器能力，应用代码不能完全替代。
- 确认数据库、备份和日志文件权限、轮转、磁盘余量和恢复演练。
- 为安全审计日志建立至少一种外部留存或告警通道，避免攻击者同时清理应用数据库和本地日志。

### 需要第三方凭据或服务

- Sentry DSN 或其他外部告警渠道：用于把严重安全事件推送到站外。
- 如果以后需要 Cloudflare API 自动改规则，还需要对应的最小权限 API Token。

### 需要明确决策后才能做

- Git 历史重写/清理属于不可逆且会影响协作者的操作，仍需单独确认后执行。
- 更强的投票防刷（设备绑定、验证码、账号门槛、行为风控）暂不做，只有实际滥用达到阈值再评估。

## 五、资源占用预估

以下是设计估算，正式部署后应以管理端事件量和 SQLite 文件增长实测校正。

| 项目 | 影响 | 预估 |
| --- | --- | --- |
| 用户端网络 | 不新增安全请求，不上传审计正文 | 基本为 0；不影响弱网往返次数 |
| 用户端 CPU/内存 | 投票限流只查轻量配额；普通接口不执行管理审计 | 基本无可感知变化 |
| 管理端请求 | 每个被分类的管理请求响应结束后增加一次 SQLite 写入和一次 HMAC 计算 | 管理端低频使用时可忽略；需避免把所有用户请求纳入审计 |
| 服务端内存 | 仅保留异常告警冷却键 | 上限约 1,000 个键，量级很小 |
| 数据库空间 | 安全事件只存元数据，单条限制字段长度，保留 90 天，且有索引 | 粗略按每条 1–3 KB 计；100 条/天约 9–27 MB/90 天，1000 条/天约 90–270 MB/90 天 |
| SQLite 写入 | 管理端每次审计事件写入一次，索引带来少量写放大 | 低管理访问量下远低于用户提交和 LLM 链路；若出现扫描，应依赖外层限流而不是无限写日志 |
| 运维成本 | 需要关注审计表增长、磁盘余量和告警是否可达 | 首次部署后观察 7 天，再决定是否缩短保留期或增加聚合 |

## 六、明确边界

- 应用层审计可以发现异常管理 API 使用、蜜罐探测和审计链被修改，但无法单独证明“服务器磁盘或数据库文件没有被离线复制”。
- 如果攻击者已经取得服务器文件系统权限，必须依赖服务器权限隔离、外部日志、备份、文件完整性监控和告警来发现；这些列在外部依赖中。
- 本轮目标是“异常发生后尽快可见、可追查”，不是承诺阻止所有 Kali、代理池或换 IP 工具。

## 七、交付顺序

1. 完成当前工作区的安全审计测试和管理端查看入口。
2. 跑全套门禁并检查工作区差异。
3. 提交并推送代码。
4. 在服务器部署迁移，做投票、蜜罐、审计链和弱网冒烟验证。
5. 记录资源实际增长和告警可达性。
6. 外部权限/凭据到位后，再处理 WAF、站外告警、恢复演练和 Git 历史卫生项。
